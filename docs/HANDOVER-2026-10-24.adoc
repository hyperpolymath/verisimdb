== 2. What #299 asked for, and the honest verdict

Filed 2026-10-04, no labels, no comments. The problem statement: current
documentation described an entity as having "up to 8 modal witnesses (the
octad)" while the public API/schema is named Octad; other integration projects
still use "hexad" or fixed-count wording; future implementations may select
different modular components.

It proposed three terms and asked for four things. Verdict:

[cols="3,1,4",options="header"]
|===
|Requested |Verdict |Where

|Define the relationship between a consonance subject, its modality profile and
the eight Octad slots |*Met* |link:modality-profile.adoc[§1, §4]
|State whether a profile can omit modalities, which are required/optional, and
how version/cardinality is represented |*Met*, verified against source |§5, §6
|Add examples/tests for the supported cases |*Met* |§7, plus the contract gate
|Clarify that `HEXAD` is a legacy alias only if that remains true in VCL
|*Met* — confirmed still true in grammar v3.0 |§3
|Keep transport/schema changes separate from the terminology decision |*Met* —
no contract change; six divergences *reported* instead |§9
|A number-agnostic phrase for downstream projects |*Met* at vocabulary level
|§1
|===

[[verdict]]
**Why the issue is still open.** One implicit criterion — that the contract is
actually verified and versioned — is *not* met, and cannot be met by this change.
There is no versioned contract to cite: the JSON-Schema `$id`s are unversioned,
and the OpenAPI request body disagrees with the running server (<<divergences,§6>>,
item 1). Closing on the strength of improved wording would be exactly the failure
the issue warns about. It is referenced from the PR as *Refs*, not *Closes*.

== 3. The vocabulary as adopted

Use these three terms with these meanings, and only these meanings:

[cols="1,3,2",options="header"]
|===
|Term |Means |Cardinality

|*modality profile*
|The selection an implementation supports: the named, versioned list of modality
slots it can populate, plus the rules for what is required, optional and always
written. A property of the *implementation and its version*.
|Implementation-specific. This implementation: the Octad, exactly 8 slots, fixed.
It is **not** selectable per request, per tenant or per entity.

|*modality set*
|The membership alone: which modalities are actually present for one subject at
one moment. Says nothing about why.
|Implementation- and entity-specific. Need not be all slots; a strict subset is
normal, not an error.

|*Octad*
|VeriSimDB's specifically named eight-modality model and API — the eight slots,
`OctadInput`, `OctadStore`, `verisim-octad`.
|Exactly 8. Always. A proper noun for this project's model, not a generic word
for "a modality group".
|===

Rules that follow, and that downstream projects should be told:

* "Up to eight modal witnesses" describes **membership**, never a variable-arity
  contract. A three-modality *set* is supported and normal; a three-slot
  *profile* is not implemented.
* "Hexad" is not a generic name for a modality group. In this repository it is a
  legacy VCL keyword; elsewhere it is a project-specific label. Do not infer a
  six-slot wire format from it.
* Cardinality belongs to the profile. "Modality profile" on its own does not tell
  you 8, 6 or 3 — you have to name the profile.

=== How version and cardinality are represented today

There is no versioned profile object on the wire, and the change deliberately did
not invent one. Cardinality is expressed *implicitly and redundantly* in three
places: the modality enum, `ModalityStatus`, and the concrete store alias.

The version identifiers that actually exist:

[cols="1,2",options="header"]
|===
|Artefact |Version marker present today

|VCL grammar |`Version: 3.0` in `spec/grammar.ebnf`
|HTTP API |`connectors/shared/openapi/verisim-api-v1.yaml` — v1 only in the filename
|JSON Schema |`$id` URLs under `https://verisim.db/schema/` — *unversioned*
|Rust crates |Cargo crate versions
|===

No `profile_version`, no `cardinality` field, no schema version field. Adding one
is a contract change and therefore an owner decision, not a clarification.

== 5. `HEXAD`, settled

The issue asked for this to be clarified *only if it remains true*, so it was
checked rather than assumed. Still true:

[source,ebnf]
----
hexad_source = 'HEXAD', uuid ;
----

Present in `spec/grammar.ebnf` v3.0 (canonical) **and** its near-duplicate
`docs/vcl-grammar.ebnf`. `HEXAD` is a *source keyword* meaning "one entity,
addressed by UUID" — it selects the Octad source in a `FROM` clause. It is not a
modality profile, not a claim of six modalities, and retained only for backward
compatibility with statements already written.

Renaming or removing it changes the accepted language, so it needs an owner
decision and a grammar version bump applied to **both** copies. That is recorded
in link:modality-profile.adoc[§3] and §10 of the same document.

== 6. Divergences found — the durable payload of this work

[[divergences]]
The issue assumed "the versioned contract". There isn't one contract; there are
six descriptions of one payload (grouping JSON Schema and OpenAPI in one row),
and they disagree:

[cols="3,2,3",options="header"]
|===
|Surface |Shape |Location

|`verisim_octad::OctadInput` (domain) |nested |`rust-core/verisim-octad/src/lib.rs`
|`json-schema/octad-input.json` + OpenAPI requestBody |nested
|`connectors/shared/`
|HTTP `OctadRequest` |**flat** — `title`, `body`, `embedding`, `types`,
`relationships`, `tensor`, `provenance`, `spatial`, `metadata`
|`rust-core/verisim-api/src/lib.rs`
|gRPC `OctadCreateRequest` |flat, hand-mapped to nested
|`proto/verisim.proto`, `grpc.rs`
|GraphQL `OctadInput` |flat, but a *different* flat — `tensor_shape`/`tensor_data`,
no relationships / provenance / spatial |`graphql.rs`
|Rust connector client |nested, **posted to the flat endpoint**
|`connectors/clients/rust/src/types.rs`
|===

None of these was fixed, because each moves a wire contract or a client API,
which #299 explicitly keeps out of a terminology change. All six are written up
in link:modality-profile.adoc[§9] and in the `CHANGELOG` entry:

. *The OpenAPI request body does not match the running server.* The YAML binds
  `POST`/`PUT /api/v1/octads` to the nested schema; the handler parses the flat
  `OctadRequest`. A schema-shaped body is accepted and its nested keys are
  silently ignored — the worst of the three possible behaviours.
. *The OpenAPI description promises an automatic provenance event* ("A provenance
  `created` event is recorded automatically"). The store records provenance only
  when the caller supplies it and `create_octad_handler` adds none, so
  `provenance_chain_length` can be `0`.
. *Hand-written client input types diverge.* Rust and Elixir declare `temporal`
  (plus `name`/`description`); Zig and Julia declare a `modalities` list; core and
  schema declare neither.
. *The shipped Rust client appears to create near-empty subjects.* It posts its
  own nested `OctadInput` directly to the flat endpoint. Found by static reading
  of both sides; **not** verified end-to-end — see <<provenance,§11>>.
. *Two normative grammar copies* (`spec/grammar.ebnf`, `docs/vcl-grammar.ebnf`)
  must be edited together. Pre-existing, already an owner decision.
. *JSON-Schema `$id`s are unversioned*, so "the versioned contract" cannot be
  cited by URL alone; cite file plus git revision.

Consumers of the **flat HTTP** shape, which a change to nested would affect:
`scripts/demo-consonance.sh`, `scripts/smoke-test.sh`, `scripts/two-node-test.sh`,
`scripts/self-ingest.sh`, and `verisim-api`'s own tests. Consumers of the
**nested** shape: the schema, the OpenAPI, the domain type, the gRPC mapping and
the Rust client. That split is the real reason item 1 needs a ruling rather than
an edit.

== 7. Standards research: DEED, kyq and kyX

Done because the question "can we generate both sides from one source?" arose.
Answer, with evidence from `hyperpolymath/standards`:

*DEED is the wrong layer.* `1-formats/deed/spec/DEED-GRAMMAR-SPEC.adoc` is
v0.2.3, status **DRAFT, not ratified**; the normative grammar is `deed.abnf`
v1.2.0. Its scope is "lexical structure, concrete syntax, the document forms, the
identity rule, the conformance modes, and the validator obligation" — it models
repository identity/pedigree through four doc-heads (`estate-deed`, `repo-deed`,
`estate-atlas-deed`, `praxis-deed`), not request bodies. The typing chapter is
**PROPOSED** and outside the v0.1 conformance surface, and the estate's own
vocabulary file says "No reader enforces these obligations yet." Its validator is
`deed_lint.js` (bun), which this repository does not run. Generating
`OctadInput`/`OctadRequest` and the OpenAPI from a deed would extend an
unratified identity grammar into an interface-definition language — a standards
decision, and a wire contract pinned to something unratified.

*`kyq` is not a generator.* `metadatastician/kyq` is "Kubernetes YAML Query"
(formerly `kcq`, renamed 2026-10-14 by owner ruling D333): a KYAML parser, linter
and jq-like query engine in AffineScript targeting WASM. Its sources do not
compile yet.

*`kyX` is the codegen-shaped thing, and it is planned only.* Ruling D334 renames
the planned projection compiler `kcX` → `kyX` ("y for anything from X"); `kyq` is
one consumer of the same KYAML front end. Standards' `nostos` vocabulary file is
explicit: "Once the planned kyX projection compiler exists … None of this is
implemented."

Consequence: if deed- or schema-driven projections into OpenAPI and language
types are wanted estate-wide, that is a **feature request on kyX**. Do not build it
here first, and do not wait for it either (<<options,§8>> has a local route that
needs no dependency).

Two DEED-adjacent debts belong to *other* threads, not this one: this repository
has no `<reponame>_chora.deed` (root carries the legacy `0-AI-MANIFEST.a2ml`;
`dogfood-gate.yml` warns about it), and a `(contracts …)` vocabulary clause does
not exist in v0.1 — so a deed cannot yet act even as a pointer-plus-digest to the
canonical contract.

== 9. Decisions still needed from the owner

. **Which shape is canonical** — nested (`verisim_octad::OctadInput`, which the
  schema, OpenAPI and gRPC already map to), flat (`OctadRequest`, which every
  script and every running test speaks), or "both, for one minor version"?
. **May `deny_unknown_fields` ship now as a `400`?** (O1.) This is the only part
  of item 1 that is a safety fix rather than a taste question.
. **Item 2 direction** — delete the "automatic provenance event" sentence, or
  make the create handler actually record one? Auto-recording changes provenance
  chain lengths and therefore drift baselines, so deleting the sentence is the
  safer first step.

Nothing else in this handover is blocked on a ruling.

[[traps]]
== 12. Traps for the next person

* **Do not treat "up to 8" as API flexibility.** It is membership. This is the
  single most common misreading and the reason the issue existed.
* **Do not close #299** just because the wording improved. The contract half is
  unverified until decisions 1 and 2 are ruled and implemented.
* **`spec/grammar.ebnf` and `docs/vcl-grammar.ebnf` must move together.** Two
  normative grammars is a drift hazard, not a feature.
* **`.github/workflows/actions.lock` does not need regenerating for a `run:`
  step** — only for new `uses:` refs. Verified: `scripts/check-lock-sync.sh`
  checks `uses:` refs in both directions, not file hashes.
* **Every relative `link:` must resolve**, or it must be added to
  `scripts/doc-links-allowlist.txt` *with a reason*. The allowlist is currently
  empty on purpose.
* **`check-modality-contract.py` is deliberately narrow.** It compares, it asserts
  only facts the document states, and it does **not** encode the known-broken
  divergences as expected — a gate that freezes a known break stops reporting it.
* **Do not write Rust-method shorthand as `T::f/0`** in these docs; that is Elixir
  arity syntax. It is `T::f()`.
