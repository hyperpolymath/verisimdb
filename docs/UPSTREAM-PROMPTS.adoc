= Upstream prompts — changes other repos need (from the 2026-10-25 verisimdb CI overhaul)
:toc: left

____
Each prompt is self-contained and copy-paste ready for a session in that
repo. They are ordered by how much of verisimdb's (and the estate's) CI
they unblock. Nothing here asks an upstream to weaken a gate.

== P-STD-1 — hyperpolymath/standards: dead pins + owner allowlist + UUID governance

....
Foundational CI fix in standards, evidence from verisimdb (2026-10-25):

1. STALE/ORPHANED PINS: three standards commit SHAs that estate callers
   pin (8f31a5a4…, cc58c0cb…, 8750b94a…) return 422 "No commit found"
   from the GitHub API in both hyperpolymath/standards and
   metadatastician/standards, so every caller workflow pinning them is
   startup_failure with zero jobs (verisimdb Governance, Hypatia,
   Scorecard were dead this way). Please: (a) publish a canonical
   "current vetted standards SHA" in a machine-readable place callers
   can poll, (b) add a standards-side CI check that samples known
   caller pins across the estate and fails when a pinned commit stops
   resolving (history rewrite/transfer detector), (c) document the
   transfer/rewrite event that orphaned these SHAs so callers can
   distinguish "bump deliberately" from "your pin no longer exists".

2. GOVERNANCE ALLOWLIST vs TRANSFERRED OWNER (from verisimdb PR #318):
   governance-reusable's language/owner allowlist rejects the
   transferred `metadatastician/standards` owner. Ratify which owner(s)
   are canonical post-transfer and make the allowlist data, not prose,
   with the transfer recorded.

3. UUID-v8 JOBS: two governance jobs reject existing non-v8
   identifiers estate-wide (e.g. verisimdb OctadId is UUIDv4 by design
   today). Ship the ratified migration story as a standards ADR +
   reusable input (report-only mode with an expiry), or every consumer
   stays red-or-exempt forever.

Acceptance: a canary caller (verisimdb) pinned to the published vetted
SHA goes green on governance + hypatia lanes with no exemptions; the
pin-resolvability check exists and is itself gated in standards CI.

== P-PTB — hyperpolymath/proven-tests-and-benches: consumer template + action

....
verisimdb is now a framework consumer (verification/proven-tests/,
an .ipkg depending on proven-tests, Idris2 installed via your
scripts/install-idris2.sh, Chez-versioned cache key copied from your
ci.yml). Adoption took reverse-engineering TypeSafeTests. Please:

1. Ship `docs/CONSUMING.adoc` + a minimal `examples/consumer/` .ipkg
   (one provisionally-proven suite, Main.idr with the exit-code idiom)
   that builds against an installed proven-tests from a *different*
   directory — your own suites build in-tree, which hides the
   installed-package path a consumer actually takes. Gate it in CI
   in a temp dir so it cannot rot in-tree.
2. Ship a composite action (attested-install style like
   cicd-squabbler's) or a reusable workflow for "install Idris2 +
   framework at pin, build and run a consumer ipkg", with the Chez
   cache key handled inside, so consumers stop copying ci.yml stanzas.
3. The legacy constructors (provisionalTest etc.) carry FixtureDebt
   "B2-LEGACY-SUITE" — consumers following TypeSafeTests inherit that
   debt label. Provide a non-legacy consumer constructor that takes a
   FixtureObligation, or document that consumers should classify
   directly; today the worked examples teach the debt path.
4. Ratify or retire the 17th category (TypeSafeTest vs the estate's
   16, DEBT S-4): verisimdb's evidence registry uses its own category
   vocabulary partly because the standard one is ambiguous here.

Acceptance: a fresh repo can adopt the framework from CONSUMING.adoc
alone, in under an hour, without reading TypeSafeTests.

== P-PONS — hyperpolymath/pons-asinorum: releases + a consumable scan lane

....
verisimdb builds pons from source at a pinned commit in CI
(pons scan --format sarif, --fail-on error). It works but every
consumer pays a full workspace build. Please:

1. Cut versioned releases with attested binaries (the
   cicd-squabbler release.yml pattern: sha256 + build provenance),
   at least x86_64-linux-musl, so consumers install instead of build.
2. Ship a composite action or reusable workflow: inputs path,
   fail-on, no-speculative, config; steps build/install, scan JSON +
   SARIF, upload-sarif, artifacts. Dogfood it on pons itself.
3. Consider a `--output <file>` flag: today SARIF/JSON go to stdout,
   which forces `>` redirection and makes "scan could not run" vs
   "empty report" one shell mistake apart. (Exit 2 on zero files is
   good — keep it, and document the full exit-code table in the man
   page/README top section.)
4. Publish the baseline/suppression story for large polyglot repos
   (verisimdb: Rust+Elixir+Idris+shell): pons.toml examples per
   language with required-language coverage, so first adoption on a
   big tree is triageable rather than a findings flood.

Acceptance: verisimdb's deep-recon pons job drops its cargo build,
keeps identical gating, and runs in <5 min warm.

== P-PANIC — hyperpolymath/panic-attack: scan-and-report hardening

....
verisimdb pins scan-and-report.yml@b553083… and also runs assail
directly. Issues in the reusable itself (estate blast radius):

1. `panic-attack assail ${{ inputs.repo_path }} --output ...` puts a

   was superseded by a manual bump to b553083 in a full CI overhaul —
   a CHANGELOG "reusable contract" section (inputs/secrets/exit
   semantics per commit range) would let dependabot PRs be assessed
   without diffing the workflow.

Acceptance: scan-and-report at a new pin installs panic-attack at that
same commit, no ${{ }} in run:, and verisimdb re-pins cleanly.

== P-KYQ — metadatastician/kyq (+ KYAML in standards): the gate interface

....
Estate policy says kyq is "the intended repository gate interface"
for TOML/Dhall/KYAML/I-JSON-JCS, and also that kyq does not yet
compile on AffineScript 0.1.1. Until it lands, consumers (verisimdb
included) wire yq + ijson-jcs directly — fine, but the interface
should stabilise *before* the implementation swaps:

1. Publish the kyq gate CLI contract (subcommands, exit codes,
   JSON verdict schema) as a standards doc, with the current
   yq/ijson-jcs shell implementations as the reference backend, so
   repos can code to the contract now and swap binaries later.
2. KYAML in workflows (standards Y-3 step 6): verisimdb's
   elixir-ci.yml and ghcr-publish.yml are good torture tests (long
   run: bodies, heredocs, ${{ }} braces vs KYAML flow braces). Add
   them (or equivalents) to the yaml-comment-proof corpus — if the
   proof covers those, step 6 is mechanical estate-wide.

Acceptance: a written kyq contract + corpus entries for workflow-
shaped YAML; verisimdb's check-kyaml.sh becomes a contract caller.
